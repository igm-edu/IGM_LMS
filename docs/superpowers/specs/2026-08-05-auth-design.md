# 인증 설계 문서

작성일: 2026-08-05
상위 문서: `2026-08-05-lms-design.md` (6장 API 규약, 7장 인증과 보안)

기반 문서가 정한 인증 방침을 구현 가능한 수준으로 구체화한다. 상위 문서와 어긋나는 부분은 이유를 함께 적었다.

## 1. 범위

브라우저에서 회원가입하고 로그인해 본인 정보가 화면에 표시되는 것까지가 이 작업의 끝이다. GitHub Pages에 배포된 정적 화면이 Apps Script 웹앱과 실제로 통신하는 상태를 만든다.

포함하는 것은 요청 라우팅과 권한 검사, 세션 발급·검증, 회원가입·로그인·로그아웃·내 정보 조회·프로필 수정 API, 그리고 로그인·회원가입 화면과 프론트 통신 모듈이다.

포함하지 않는 것은 클래스·차시·퀴즈·수료증 기능과 관리자·강사 화면이다. 관리자의 임시 비밀번호 발급도 회원 관리 기능과 함께 다음 작업으로 미룬다.

## 2. 전제

기반 작업이 이미 제공하는 것 위에 쌓는다.

- `apps-script/schema.js` — 13개 시트 정의. Users와 Sessions의 열 구성은 여기서 온다.
- `apps-script/lib/sheet.js` — `readAll`, `findByPk`, `findBy`, `insert`, `update`, `upsert`, `deleteByPk`, `newId`. 실행 단위로 스프레드시트 핸들을 메모이즈하며, `insert`는 기본키 중복을 거부한다.
- `apps-script/lib/hash.js` — `hashPassword`, `verifyPassword`, `generateToken`, `sha256Hex`. PBKDF2 반복 횟수는 3,000회로 확정되어 있다.
- `test/helpers/gas-shim.js`, `test/helpers/sheets-fake.js` — Node에서 Apps Script 전역과 Sheets를 대신하는 대역.

Apps Script 하루 총 실행시간 90분이라는 무료 계정 할당량은 그대로 설계 상수다.

## 3. 파일 구조

```
apps-script/
  main.js              doPost / doGet 진입점, 라우팅 표, 권한 검사, 오류 처리
  handlers/auth.js     signup · login · logout · me · updateProfile
  lib/session.js       토큰 발급 · 검증 · 연장 · 폐기
  lib/sheet.js         (수정) findByColumn 추가
index.html             로그인 · 회원가입 화면
assets/js/config.js    웹앱 엔드포인트 주소
assets/js/api.js       통신, 재시도, 응답 해석, 토큰 첨부
assets/js/auth.js      토큰 보관, 로그인 상태 관리
assets/css/style.css
```

화면이 하나뿐인 시점에 프론트를 세 모듈로 나누는 것이 과해 보일 수 있으나, 이 세 파일은 이후 모든 화면이 공유하는 토대다. 나중에 분리하면 이미 여러 화면이 각자 방식으로 통신하고 있어 되돌리기 어렵다.

## 4. 요청과 응답

단일 엔드포인트에 POST하고 본문의 `action`으로 분기한다.

요청: `{ "action": "...", "token": "...", "payload": { ... } }`
응답: `{ "ok": true, "data": ... }` 또는 `{ "ok": false, "error": { "code": "...", "message": "..." } }`

Apps Script 웹앱은 항상 HTTP 200을 반환하므로 성공 여부는 본문의 `ok`로만 판단한다.

### 4.1 CORS 제약

Apps Script 웹앱은 브라우저의 CORS 사전 요청(preflight)에 응답할 수 없다. 사전 요청이 발생하지 않는 단순 요청 조건을 반드시 지켜야 한다.

- 본문은 JSON 문자열로 만들되 `Content-Type`은 `text/plain;charset=utf-8`로 보낸다.
- 사용자 정의 헤더를 쓰지 않는다. **세션 토큰은 헤더가 아니라 본문에 담는다.**
- 서버는 `e.postData.contents`를 문자열로 받아 직접 파싱한다.

이 조건을 어기면 통신 자체가 실패하며, 브라우저 콘솔에는 원인을 짐작하기 어려운 CORS 오류만 남는다.

`doGet`은 배포 확인용으로 상태 문자열만 반환한다. 데이터를 다루지 않는다.

## 5. 라우팅과 권한 검사

권한 검사를 각 핸들러에 흩어 두면 언젠가 한 곳이 빠진다. 라우팅 표에 기능별 요구 역할을 선언하고 진입 지점에서 일괄 확인한다.

```js
var ROUTES = {
  'auth.signup':        { handler: handleSignup,        roles: PUBLIC },
  'auth.login':         { handler: handleLogin,         roles: PUBLIC },
  'auth.logout':        { handler: handleLogout,        roles: ANY_USER },
  'auth.me':            { handler: handleMe,            roles: ANY_USER },
  'auth.updateProfile': { handler: handleUpdateProfile, roles: ANY_USER },
};
```

`PUBLIC`이 아닌 항목은 토큰 검증을 통과해야만 핸들러에 도달한다. 검증된 사용자 객체는 핸들러에 인자로 전달되므로, 핸들러가 토큰을 다시 다룰 일이 없다.

역할 제한이 필요한 기능은 `roles: ['admin']` 형태로 적는다. 이번 범위에는 해당 항목이 없으나 검사 로직은 배열을 처리하도록 만든다. 다음 작업에서 관리자 전용 기능이 바로 붙는다.

알 수 없는 `action`은 `UNKNOWN_ACTION`으로 거부한다.

## 6. 오류 처리

**예상된 실패와 예기치 못한 실패를 구분한다.** 구분하지 않으면 정상적인 로그인 실패가 ErrorLog 시트를 채우고, 그 안에 진짜 버그가 묻힌다.

핸들러는 예상된 실패에 코드를 붙여 던진다.

```js
throw appError_('INVALID_CREDENTIALS', '이메일 또는 비밀번호가 올바르지 않습니다.');
```

진입 지점의 예외 처리는 두 가지를 나눈다. `appCode`가 붙은 예외는 그 코드와 메시지를 그대로 응답하고 ErrorLog에 남기지 않는다. 그 외 예외는 ErrorLog에 요청 종류·회원·시각·메시지·스택을 기록하고, 사용자에게는 `INTERNAL` 코드와 일반 문구만 반환한다. 내부 사정은 응답에 노출하지 않는다.

사용하는 오류 코드는 다음과 같다.

| 코드 | 의미 |
|---|---|
| `UNKNOWN_ACTION` | 정의되지 않은 action |
| `BAD_REQUEST` | 필수 입력 누락, 형식 위반 |
| `INVALID_CREDENTIALS` | 로그인 실패 (이메일 없음과 비밀번호 불일치를 구분하지 않음) |
| `EMAIL_TAKEN` | 가입 시 이미 사용 중인 이메일 |
| `ACCOUNT_LOCKED` | 로그인 시도 제한에 걸림 |
| `ACCOUNT_INACTIVE` | 비활성 상태 계정 |
| `TOKEN_INVALID` | 토큰이 없거나 유효하지 않음 |
| `TOKEN_EXPIRED` | 토큰 만료 |
| `FORBIDDEN` | 역할 권한 부족 |
| `INTERNAL` | 그 외 예외 |

프론트는 `TOKEN_INVALID`와 `TOKEN_EXPIRED`를 받으면 저장된 토큰을 지우고 로그인 화면으로 보낸다.

## 7. 세션

`lib/session.js`가 담당한다.

**발급.** `generateToken()`으로 만든 원문은 브라우저에만 주고, Sessions 시트에는 SHA-256 해시를 기본키로 저장한다. 스프레드시트가 유출되어도 그 값으로 바로 로그인할 수 없게 하기 위해서다. 유효기간은 발급 시점부터 24시간이다.

**검증.** 토큰 해시로 Sessions를 조회한다. 이 시트는 토큰 해시가 기본키라 기존 행 인덱스 캐시를 그대로 탄다. 만료를 확인한 뒤 `user_id`로 Users를 조회하고, 계정 상태가 `active`인지 본다. 관리자가 회원을 비활성화하면 이미 발급된 토큰도 즉시 통하지 않아야 한다.

**연장.** 만료가 6시간 이내로 남은 요청에서 만료 시각을 다시 24시간 뒤로 민다. 여기에 의도한 부수효과가 있다. 한 번 연장하면 남은 시간이 24시간이 되어 이후 18시간 동안 연장 조건에 걸리지 않으므로, 별도 장치 없이 시트 쓰기가 자연히 제한된다. 긴 영상을 보는 도중 로그아웃되는 상황을 막으면서 할당량도 아낀다.

**폐기.** 로그아웃은 해당 Sessions 행을 삭제한다.

만료된 행의 정리는 이 작업 범위가 아니다. 상위 문서 9.1절이 정한 일일 트리거에서 함께 처리한다.

## 8. 회원가입

받는 항목은 이름, 이메일, 비밀번호, 연락처, 소속, 직급, 생년월일, 그리고 개인정보 수집·이용 동의다. 동의하지 않으면 진행되지 않으며 동의 시각을 `consent_at`에 기록한다. `retention_until`은 가입일로부터 3년이다.

**비밀번호 정책은 8자 이상이며 영문과 숫자를 모두 포함해야 한다.** 기록해 둘 점이 있다. 길이만 요구하고 문자 조합은 강제하지 않는 편이 실제 방어력이 높다는 것이 NIST 권고 이후의 통설이지만, 국내 기업 사용자에게 익숙한 형태를 택해 문의 부담을 줄이는 쪽으로 결정했다. 이 정책은 해싱 반복 횟수 3,000회의 한계를 보완하는 방어선 중 하나이므로, 향후 운영 계정이나 백엔드가 바뀌면 함께 재검토한다.

검증을 통과하면 계정을 만들고 **토큰까지 발급해 로그인 상태로 넘긴다.** 상위 문서가 별도 승인 절차 없이 가입 즉시 이용 가능하다고 정했으므로, 가입 직후 다시 로그인을 요구하는 것은 불필요한 마찰이다.

**계정 열거에 대한 비대칭 처리.** 가입 화면에서는 이미 사용 중인 이메일임을 알려준다(`EMAIL_TAKEN`). 알려주지 않으면 사용자가 막힌 이유를 알 수 없다. 반면 로그인 화면에서는 이메일 존재 여부를 절대 노출하지 않는다. 로그인 쪽이 공격자가 계정 목록을 캐낼 때 실제로 쓰는 통로이기 때문이다.

### 8.1 이메일 정규화

**이메일은 저장 전에 앞뒤 공백을 제거하고 소문자로 바꾼다.** 가입·로그인·중복 검사 모두 이 정규화를 거친 값을 쓴다.

정규화하지 않으면 `Hong@igm.co.kr`로 가입한 사람이 `hong@igm.co.kr`로 로그인할 때 실패한다. 더 나쁜 경우는 중복 검사가 대소문자만 다른 주소를 다른 것으로 판정해 같은 사람의 계정이 두 개 만들어지는 것이다. 이메일 주소의 도메인 부분은 원래 대소문자를 구분하지 않고, 로컬 부분을 구분하는 메일 서버는 현실에 거의 없다.

정규화는 순수 함수 하나로 분리해 가입·로그인·중복 검사가 모두 같은 함수를 거치게 한다. 세 곳에 흩어 적으면 한 곳이 빠졌을 때 증상이 "어떤 사용자만 로그인이 안 됨"으로 나타나 원인을 찾기 어렵다.

## 9. 로그인

**시도 제한.** 같은 계정에 5회 연속 실패하면 10분 잠근다. Apps Script는 접속자 IP를 알 수 없어 이메일 기준으로만 셀 수 있으며, 카운터는 `CacheService`에 둔다. 성공하면 카운터를 지운다. 완벽하지는 않지만 무차별 대입은 실질적으로 막힌다.

잠긴 상태에서 들어온 시도는 비밀번호를 검증하지 않고 즉시 `ACCOUNT_LOCKED`로 거부하며, **카운터를 더 늘리지 않는다.** 늘리면 공격자가 요청을 계속 보내는 것만으로 잠금을 무한히 연장해 정당한 사용자를 영구히 차단할 수 있다. 검증을 건너뛰므로 잠긴 계정에 대한 요청은 해싱 비용도 소모하지 않는다.

**조회.** 이메일로 사용자를 찾는다. 상세는 10장에 적었다.

**비밀번호 검증을 예외 처리로 감싼다.** 기반 작업에서 손상된 저장값이 예외를 던지던 경로는 막았으나, 시트를 사람이 직접 편집할 수 있는 구조인 이상 한 계정의 데이터가 깨졌다고 로그인 기능 전체가 죽어서는 안 된다. 예외가 나면 그 계정만 `INVALID_CREDENTIALS`로 실패시키고, 원인 파악을 위해 ErrorLog에는 남긴다.

계정 상태가 `active`가 아니면 `ACCOUNT_INACTIVE`로 거부한다.

## 9.1 프로필 수정

`auth.updateProfile`은 본인 계정만 수정한다. 대상 사용자는 토큰에서 확인한 사용자이며, 요청 본문의 `user_id`는 무시한다. 받아서 쓰면 남의 계정을 고칠 수 있는 통로가 된다.

수정할 수 있는 필드는 `name`, `phone`, `company`, `position`, `birth_date` 다섯 개다. 화이트리스트 방식으로 처리하며 목록에 없는 필드는 조용히 버린다.

수정할 수 없는 항목과 이유는 다음과 같다. `email`은 로그인 ID이므로 중복 검사와 세션 처리가 함께 필요해 별도 기능으로 다룬다. `role`과 `status`는 관리자만 바꿀 수 있어야 하며 회원 관리 기능에 속한다. `password_hash`는 비밀번호 변경 기능이 따로 있어야 한다. `consent_at`, `retention_until`, `created_at`, `user_id`는 기록이지 입력이 아니다.

비밀번호 변경과 이메일 변경은 이번 범위에 넣지 않는다. 둘 다 현재 비밀번호 재확인이 필요하고, 이메일 변경은 세션 처리까지 얽혀 별도로 설계할 값어치가 있다.

## 10. 이메일 조회 (`findByColumn`)

Users의 기본키는 `user_id`인데 로그인은 `email`로 사용자를 찾는다. 현재의 `findBy`는 `readAll`을 호출해 시트 전체(13개 열 × 전체 행)를 읽은 뒤 메모리에서 훑는다.

`lib/sheet.js`에 열 하나만 읽는 조회를 추가한다.

```
findByColumn(name, field, value) -> object | null
```

지정한 열 하나만 읽어 일치하는 행 번호를 찾고, 그 행만 다시 읽어 객체로 돌려준다. 호출은 두 번이지만 각 payload가 훨씬 작아 전체 읽기보다 빠르고, 사용자가 늘어도 완만하게 증가한다. 시트를 추가하지 않으므로 동기화 대상이 생기지 않는다.

일치하는 행이 여럿이면 **가장 위의 행 하나만** 돌려준다. 기존 `findBy`와 같은 계약이다. 이메일 중복은 가입 단계에서 막지만 관리자가 시트를 직접 편집해 만들 수 있으므로, 그 경우에도 동작이 예측 가능해야 한다. 값을 찾지 못하면 `null`이다. 정의되지 않은 열 이름을 넘기면 예외를 던진다.

인덱스 전용 시트(`email → user_id`)를 두는 방안도 검토했으나, 가입과 이메일 변경마다 두 곳을 맞춰야 하고 어긋나면 로그인이 조용히 실패한다. 수십~수백 명 규모에서 그 위험을 감수할 이유가 없다. 사용자가 수천 명대에 이르면 그때 전환한다.

## 11. 응답 직렬화

사용자 정보를 돌려주는 곳은 가입 응답, 로그인 응답, `auth.me` 세 군데다. 시트에서 읽은 행을 그대로 내보내면 `password_hash`가 브라우저까지 간다.

응답용 객체를 만드는 함수를 한 곳에 두고 모든 경로가 이를 거치게 한다. 이 함수는 화이트리스트 방식으로, 내보낼 필드를 명시적으로 나열한다. 시트에 열이 추가되어도 자동으로 새어 나가지 않게 하기 위해서다.

내보내는 필드는 `user_id`, `name`, `email`, `phone`, `company`, `position`, `role`, `status`, `created_at`이다. `password_hash`, `birth_date`, `consent_at`, `retention_until`은 내보내지 않는다. 생년월일은 수료증 발급에만 쓰이므로 화면에 내려보낼 이유가 없다.

**이 함수가 `password_hash`를 포함하지 않는다는 것만 검증하는 테스트를 따로 둔다.** 나중에 필드를 추가하다 통째로 내보내는 실수를 막는 장치다.

## 12. 프론트엔드

`config.js`는 웹앱 엔드포인트 주소만 담는다. 이 주소는 비밀이 아니다. 토큰 없이는 어떤 데이터도 반환하지 않기 때문이다.

`api.js`가 모든 통신을 담당한다. 4.1절의 단순 요청 조건을 지켜 요청을 만들고, 저장된 토큰이 있으면 본문에 실으며, 응답의 `ok`를 해석한다. 네트워크 오류는 간격을 늘려가며 두 번까지 자동 재시도한다. `TOKEN_INVALID`나 `TOKEN_EXPIRED`를 받으면 토큰을 지우고 로그인 화면으로 보낸다.

`auth.js`는 토큰을 `localStorage`에 보관하고 로그인 상태를 관리한다.

`index.html`은 로그인 폼과 회원가입 폼을 전환하는 한 장짜리 화면이다. 로그인하면 이름과 소속을 표시하는 간단한 영역을 보여준다. 이 영역은 다음 작업에서 클래스 목록으로 대체된다.

**사용자가 입력한 값은 HTML로 조립하지 않고 `textContent`로만 넣는다.** 토큰을 `localStorage`에 두는 이상 스크립트 주입은 곧 토큰 탈취로 이어진다. 외부 스크립트도 페이지에 넣지 않는다.

## 13. 테스트

Sheets에 의존하지 않는 판정 로직은 순수 함수로 분리해 Node에서 검증한다. 비밀번호 정책, 이메일 형식, 세션 만료·연장 판정, 로그인 시도 제한 카운터가 여기 해당한다. 세션 판정은 현재 시각을 인자로 받게 만들어 경계값을 직접 넣는다.

그 위에 통합 테스트를 얹는다. 기반 작업의 메모리 대역 덕분에 `doPost`부터 시트 쓰기까지 전 과정을 Node에서 돌릴 수 있다. 다음을 검증한다.

- 가입 → 로그인 → 내 정보 조회가 한 흐름으로 동작한다
- 토큰 없이 보호된 기능을 부르면 거부된다
- 만료된 토큰이 거부된다
- 만료가 임박한 토큰은 연장되고, 방금 연장된 토큰은 다시 연장되지 않는다
- 5회 실패 후 잠기고, 성공하면 카운터가 지워진다
- 없는 이메일과 틀린 비밀번호가 같은 오류 코드와 메시지를 반환한다
- 응답 어디에도 `password_hash`가 없다
- 비활성 계정은 로그인할 수 없고, 이미 발급된 토큰도 통하지 않는다
- 라우팅 표의 `PUBLIC`이 아닌 모든 action이 토큰을 요구한다
- 대문자가 섞인 이메일로 가입한 계정이 소문자로 로그인되고, 대소문자만 다른 주소로는 중복 가입이 되지 않는다
- 잠긴 계정에 추가 시도를 보내도 잠금 시간이 연장되지 않는다
- `updateProfile`이 요청 본문의 `user_id`를 무시하고 토큰의 사용자만 수정한다
- `updateProfile`이 `role`, `status`, `email`, `password_hash`를 바꾸지 못한다

`api.js`는 `fetch`를 대역으로 바꿔 응답 해석과 재시도를 Node에서 검증한다. 화면 동작만 브라우저에서 직접 확인한다.

## 14. 배포

Apps Script 웹앱을 "나로 실행 / 모든 사용자 액세스 가능"으로 배포하고, 발급된 URL을 `config.js`에 넣는다.

GitHub Pages는 저장소 설정에서 활성화해야 한다. 이 저장소는 공개 상태이므로 무료 플랜에서 사용할 수 있다. 소스는 `main` 브랜치 루트로 지정한다. `.nojekyll`은 기반 작업에서 이미 추가되어 있다.

Pages 활성화는 저장소 설정 변경이므로 담당자가 직접 수행한다.

## 15. 이후 확정할 사항

구현을 막지 않으나 진행 중 확인이 필요한 항목이다.

- 관리자의 임시 비밀번호 발급 — 회원 관리 기능과 함께 다음 작업으로
