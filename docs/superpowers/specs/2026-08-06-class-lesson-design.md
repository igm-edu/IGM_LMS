# 클래스·차시 관리 설계 문서

작성일: 2026-08-06
상위 문서: `2026-08-05-lms-design.md` (3.2 클래스 관리, 3.3 차시 및 영상 관리, 6장 API 규약)
선행 작업: 기반 구조, 인증 백엔드, 인증 프론트엔드 — 모두 main에 병합 완료

---

## 1. 범위

관리자가 클래스를 개설하고 그 아래에 차시를 등록하는 것까지다. 이 작업이 끝나면 실제 과정 데이터가 시스템 안에 들어오고, 이후의 수강 신청·시청·퀴즈가 붙을 자리가 생긴다.

**수강 신청(`class.enroll`)은 포함하지 않는다.** 학습 화면이 없는 상태에서 신청해도 아무 일이 일어나지 않아 확인할 방법이 없다. 수강생 학습 흐름과 함께 다음 작업으로 묶는다.

퀴즈 등록, 시청시간 측정, 출결·수료 판정, 강사 대시보드도 이번 범위 밖이다.

## 2. 전제

이미 만들어져 있고 그대로 쓴다.

- `apps-script/main.js` — `doPost` 진입점, `routes_()` 라우팅 표, 권한 검사, `appError_`/`isAppError_` 기반 오류 분리, ErrorLog 기록
- `apps-script/lib/sheet.js` — `readAll`, `findByPk`, `findBy`, `findByColumn`, `insert`, `update`, `upsert`, `deleteByPk`, `newId`
- `apps-script/lib/validate.js` — `requireFields` 등
- `apps-script/lib/errors.js` — `appError_`
- `apps-script/schema.js` — Classes와 Lessons의 열 구성은 여기서 온다
- 프론트 `assets/js/api.js`, `assets/js/auth.js`

Apps Script 하루 총 실행시간 90분 제약은 그대로 유효하다.

## 3. 이 작업에서 처음 실행되는 권한 분기

**지금까지 라우팅 표에는 `PUBLIC`과 `ANY_USER`만 있었다.** `main.js`의 역할 배열 검사(`route.roles.indexOf(...)`)는 한 번도 실행된 적 없는 코드다. 이번에 `roles: ['admin']` 항목이 세 개 들어가면서 그 분기가 처음 돌게 된다.

기반 작업의 최종 리뷰가 이 지점을 명시적으로 지목했으므로, 다음 두 가지를 반드시 테스트로 고정한다.

- 학생 역할 토큰으로 관리자 전용 action을 부르면 `FORBIDDEN`이 반환된다
- 관리자 토큰으로는 통과한다

`roles`에 배열이 아닌 값을 넣었을 때 요청을 막는 방어는 이미 들어가 있다.

## 4. API

| action | 권한 | 설명 |
|---|---|---|
| `class.list` | 회원 | 클래스 목록. 관리자는 전부, 그 외에는 모집중·진행중만 |
| `class.get` | 회원 | 클래스 하나와 그 차시 목록 |
| `class.upsert` | 관리자 | 클래스 개설·수정 |
| `lesson.upsert` | 관리자 | 차시 등록·수정 |
| `lesson.delete` | 관리자 | 차시 삭제 (조건부) |

### 4.1 신규와 수정의 구분

`class.upsert`와 `lesson.upsert`는 요청에 식별자(`class_id` / `lesson_id`)가 있으면 수정, 없으면 신규로 본다.

식별자가 있는데 해당 행이 없으면 **거부한다.** 없는 행을 새로 만들어 주면, 관리자가 오타 난 ID로 수정을 시도했을 때 조용히 엉뚱한 클래스가 하나 더 생긴다. 실수가 오류가 아니라 데이터로 남는 형태다.

**수정은 요청에 담긴 항목만 반영한다.** 담기지 않은 항목은 기존 값을 그대로 둔다. 빠진 것을 기본값으로 덮어쓰면 이름만 고치려던 요청이 담당 강사와 운영 기간과 상태를 조용히 지운다. 오류도 나지 않고 저장 성공으로 보인다. 비우려는 의도라면 빈 값을 명시적으로 보내면 된다.

`class_name`, `batch`, `watch_rate_threshold`, `quiz_pass_score`는 예외로 항상 필요하다. 빠지면 조용히 사라지는 대신 검증에서 걸려 요청 자체가 실패한다.

차시에는 예외가 하나 더 있다. **영상 주소를 바꿀 때는 영상 길이도 함께 보내야 한다.** 주소만 갈면 이전 영상의 길이가 그대로 남아 시청률 분모가 틀어지는데, 오류 없이 잘못된 수료 판정으로만 드러난다. 반대로 길이만 고치는 것은 허용한다. 자동 측정이 틀렸을 때 손으로 바로잡는 경로다.

차시 제목을 빈 값으로 보내면 거부한다. 필수 항목을 비우려는 요청을 조용히 무시하지 않는다는 원칙은 프로필 수정과 같다.

수정할 때 `class_id`와 `lesson_id` 자체는 바꿀 수 없다. 차시의 소속 클래스(`class_id`)도 바꿀 수 없다. 옮기는 기능이 필요해지면 그때 따로 설계한다.

### 4.2 상태 값

`Classes.status`는 `모집중`, `진행중`, `종료` 셋 중 하나여야 한다. 다른 값을 받으면 거부한다. 검증하지 않으면 오타 난 상태의 클래스가 `class.list`의 어느 필터에도 걸리지 않아 목록에서 사라진다. 신규 생성 시 값을 주지 않으면 `모집중`으로 둔다.

`class.list`가 역할에 따라 다른 결과를 주는 이유는 종료된 기수를 수강생 화면에 늘어놓을 이유가 없기 때문이다. 이 필터는 서버에서 건다. 프론트에서 거르면 응답에는 이미 데이터가 실려 있어 개발자 도구로 보인다.

**클래스 삭제는 만들지 않는다.** 상태를 "종료"로 바꾸면 충분하고, 삭제는 되돌릴 수 없는데 얻는 것이 없다. 수강 이력이 딸린 클래스를 지우는 실수는 복구가 불가능하다.

## 5. 입력 검증

### 5.1 담당 강사

`instructor_id`는 실제로 존재하는 사용자여야 하고 역할이 `instructor` 또는 `admin`이어야 한다. 확인하지 않으면 오타 하나로 존재하지 않는 강사가 배정된 클래스가 만들어지고, 나중에 강사 대시보드가 붙었을 때 그 클래스는 아무에게도 보이지 않는다. 비워두는 것은 허용한다 — 강사가 아직 정해지지 않은 시점에 클래스를 먼저 열 수 있어야 한다.

### 5.2 기준값

`watch_rate_threshold`와 `quiz_pass_score`는 0 이상 100 이하의 수여야 한다. 범위를 보지 않으면 120 같은 값이 들어가 아무도 수료할 수 없는 클래스가 조용히 만들어진다. 판정 로직은 정상 동작하므로 오류도 나지 않고, 수강생이 전부 이수했는데 수료 처리가 안 되는 상황으로만 드러난다.

### 5.3 운영 기간

`start_date`가 `end_date`보다 늦으면 거부한다.

### 5.4 영상 URL

**HTTPS만 받는다.** GitHub Pages가 HTTPS로 서빙되므로 HTTP 영상은 브라우저가 혼합 콘텐츠로 차단한다. 등록 시점에 막지 않으면 수강생이 재생 버튼을 눌러야 비로소 문제가 드러난다.

### 5.5 영상 길이

`video_duration_sec`는 0보다 큰 수여야 한다. 이 값은 모든 시청률 계산의 분모다.

## 6. 영상 길이 자동 측정

관리자가 영상 URL을 붙여넣으면 **브라우저가 영상 메타데이터를 읽어 길이를 채운다.** 숨겨진 `video` 요소에 URL을 넣고 `loadedmetadata` 이벤트에서 `duration`을 가져오는 방식이다.

손으로 초를 입력하게 하지 않는 이유가 있다. 30분짜리 영상을 1800이 아니라 30으로 적는 실수는 흔한데, 그러면 그 차시는 몇 초만 봐도 100% 시청으로 집계된다. **틀려도 아무 오류가 나지 않고 잘못된 수료증이 발급되는 것으로만 드러난다.**

자동 측정은 부수 효과로 URL이 실제로 재생 가능한지도 확인해 준다. 메타데이터를 읽지 못하면 그 URL은 수강생 브라우저에서도 재생되지 않는다.

측정에 실패하면 사유를 표시하고 수동 입력을 허용한다. 자동 측정만 고집하면 일시적인 네트워크 문제로 차시를 등록하지 못하는 상황이 생긴다. 측정 성공 후에도 값을 고칠 수 있게 둔다.

측정은 프론트에서만 한다. 서버에서 `UrlFetchApp`으로 확인하는 방안도 있으나, 영상 파일을 Apps Script가 받아오면 하루 90분 실행시간을 크게 먹는다.

## 7. 차시 순서

`lesson_order`는 등록 시 자동으로 부여한다. 해당 클래스의 마지막 순서에 1을 더한 값이다. 관리자가 수정할 수 있으며, 중복된 값이 있어도 거부하지 않는다.

중복을 막지 않는 이유는 순서를 바꾸는 작업이 본질적으로 중간 상태를 거치기 때문이다. 3번과 5번을 맞바꾸려면 잠시 같은 번호가 둘 생기거나 임시 번호가 필요하다. 대신 조회할 때 `lesson_order` 다음에 `lesson_id`로 정렬해 순서가 흔들리지 않게 한다.

## 8. 차시 삭제

**시청 기록이 하나라도 있으면 삭제를 거부한다.** WatchLogs에 그 `lesson_id`가 존재하는지 확인한다.

지우면 두 가지가 무너진다. 수강생의 학습 이력이 조용히 사라지고, 클래스 평균 시청률의 분모가 되는 차시 수가 바뀌어 이미 내려진 수료 판정까지 달라진다. 기록이 없는 차시, 즉 잘못 만들었다가 바로 지우는 경우만 허용한다.

거부할 때는 왜 지울 수 없는지와 몇 명이 이미 시청했는지를 함께 알려준다. "삭제할 수 없습니다"만 나오면 관리자는 시스템이 고장 난 줄 안다.

## 9. 응답 직렬화

클래스와 차시에는 개인정보가 없으므로 인증 때와 같은 화이트리스트가 필요하지 않다. 시트 행을 그대로 내보낸다.

다만 `class.get`이 담당 강사 정보를 함께 줄 때는 `publicUser_`를 거친다. 강사도 Users 행이므로 그대로 내보내면 `password_hash`가 실린다.

## 10. 테스트 전략

Sheets에 의존하지 않는 판정 로직은 순수 함수로 분리해 Node에서 검증한다. 기준값 범위 검사, 날짜 순서 검사, HTTPS 검사, 다음 차시 순서 계산이 여기 해당한다.

그 위에 기존 메모리 대역을 그대로 써서 `doPost` 통합 테스트를 얹는다. 다음을 확인한다.

- 학생 토큰으로 관리자 전용 action을 부르면 `FORBIDDEN`이고, 관리자 토큰으로는 통과한다 (3장)
- 존재하지 않는 `instructor_id`나 강사가 아닌 사용자를 지정하면 거부된다
- 기준값이 범위를 벗어나면 거부된다
- HTTP 영상 URL이 거부된다
- 차시를 연속 등록하면 순서가 1, 2, 3으로 붙는다
- 시청 기록이 있는 차시는 삭제되지 않고, 없는 차시는 삭제된다
- `class.list`가 학생에게는 종료된 클래스를 주지 않고 관리자에게는 준다
- `class.get` 응답 어디에도 `password_hash`가 없다
- 없는 `class_id`로 수정을 시도하면 새로 만들지 않고 거부한다
- 정의되지 않은 `status` 값이 거부된다
- 차시의 `class_id`를 다른 클래스로 바꾸려는 요청이 무시되거나 거부된다

## 11. 이후 확정할 사항

- 클래스별 모집 정원 — 상위 문서가 "우선 무제한"으로 정했다. 필요해지면 `Classes`에 열을 추가한다.
- 차시 순서 재배치 UI — 이번에는 순서 값을 직접 고치는 방식으로 두고, 끌어서 옮기는 방식은 차시 수가 많아지면 검토한다.
- 클래스 복제 — 같은 과정을 다음 기수로 열 때 유용하겠으나 지금은 필요를 확인하지 못했다.
